# 外部依赖稳定性与故障可恢复性修改技术方案

> 状态：待确认
>
> 日期：2026-08-06
>
> 范围：实时转写、Codex app-server、局域网访客页、会中故障反馈
>
> 依据：2026-08-06 会中实际故障、运行日志、SQLite 状态、构建产物和本地协议验证

## 1. 背景

本次会中同时暴露了三类问题：

| 能力 | 用户看到的现象 | 已确认原因 | 当前设计缺陷 |
| --- | --- | --- | --- |
| 实时转写 | “实时转写暂时不可用”，不知道为什么、是否会恢复 | ASR 会话在产生 3 条 final 后被归类为 `ASR_PROTOCOL_INCOMPATIBLE`；多个解析或时间边界异常被直接判定为不可重试 | 故障分类过粗，单次异常即可耗尽整个能力；内部原因没有进入可用诊断信息 |
| Codex | “当前 Codex 版本暂不兼容” | Codex CLI 从 `0.146.0` 升级到 `0.146.1` 后，必要 JSON Schema 的字段顺序变化，但规范化后的语义完全一致 | 对原始文件字节做哈希，把序列化差异误判为协议不兼容 |
| 局域网访客页 | 同一 Wi-Fi 下访问链接打不开 | 服务端口已监听、API 可访问，但 `/join` 和 `/guest.html` 返回 404；当前桌面二进制没有嵌入访客页构建产物 | 静态资源装配失败被静默忽略；监听成功就被标记为“运行中”，没有验证完整入口 |

三类问题的共同根因不是“外部系统天然不稳定”，而是 MeetSieve 的可用性判定过于依赖实现细节，并且缺少自动恢复、端到端验收和可操作的错误反馈。

## 2. 用户反馈转化为工程原则

### 2.1 核心原则

1. **严格限制只用于真实风险。** 数据损坏、凭据泄漏、越权访问、不可识别的持久化结果必须阻断；JSON 字段顺序、单个网络帧异常等非语义差异不得直接阻断整项能力。
2. **先恢复，再打扰用户。** 可恢复故障默认自动重试；重试期间清晰显示状态，只有自动恢复失败后才要求用户操作。
3. **能力隔离。** 录音和本地保存是会中核心链路；ASR、Codex、LAN 任一失败都不得停止或污染录音。
4. **状态必须代表端到端事实。** “进程存在”“端口已监听”“命令可执行”都不等于功能可用。只有完成该能力最小真实闭环后才能显示“可用/运行中”。
5. **每个限制都必须可解释、可诊断、可恢复。** 用户至少能看到：什么失败、什么不受影响、系统正在做什么、下一步做什么、诊断编号是什么。
6. **不静默吞错。** 可选能力可以降级，但初始化、资源装配和协议校验错误必须进入明确状态和脱敏日志。
7. **容忍新增，阻断破坏。** 外部依赖新增可选字段、通知或文件时默认兼容；删除必要字段、改变类型、收紧必填条件或破坏调用流程时才判定不兼容。

### 2.2 故障处理基线

| 故障类型 | 默认策略 | 是否立即中断能力 | 用户反馈 |
| --- | --- | --- | --- |
| 短暂网络中断、服务端忙、单个响应损坏 | 自动重连并保留进度 | 否 | 显示“正在恢复”和重试进度 |
| 表示形式变化、未知可选字段 | 忽略未知内容并按已知语义解析 | 否 | 正常情况下不打扰用户 |
| 持续且可复现的协议破坏 | 重试确认后隔离依赖能力 | 是，仅中断对应能力 | 显示影响范围、解决入口和诊断编号 |
| 数据安全或完整性风险 | 立即阻断危险写入 | 是 | 明确说明未写入错误数据，核心录音是否仍正常 |
| 本地资源缺失或构建不完整 | 不宣称运行成功，提供修复动作 | 是，仅中断对应能力 | 显示“安装资源不完整/需要更新或重装” |

## 3. 总体状态模型

实时转写、Codex 和 LAN 统一使用以下可用性阶段，但保留各自业务状态：

```text
checking -> ready
    |         |
    |         +-> degraded -> recovering -> ready
    |                                  |
    +-------------------------------> unavailable
```

- `checking`：正在完成最小闭环检查，不提前显示“可用”。
- `ready`：已完成当前能力的真实可用性检查。
- `degraded`：功能受到影响，但核心链路或部分结果仍可用。
- `recovering`：系统正在自动恢复，必须包含当前尝试次数和下一次动作。
- `unavailable`：恢复预算耗尽或确认存在破坏性不兼容；必须附稳定错误码和用户动作。

每个快照至少包含：

```go
type CapabilityStatus struct {
    State          string
    ErrorCode      string
    ReasonCategory string
    Attempt        int
    AttemptLimit   int
    NextRetryAtMS  int64
    Unaffected     []string
    Actions        []string
    DiagnosticID   string
}
```

该结构表达产品状态，不直接透出 provider 原始错误、凭据、音频、转写正文或完整令牌。

## 4. Codex 兼容性修改

### 4.1 已确认问题

当前 `internal/adapter/agent/codex/schema_verifier.go` 对 Codex 生成的必要 Schema 文件直接计算原始字节哈希。`0.146.0` 与 `0.146.1` 的 7 个必要文件虽然哈希不同，但对 JSON 解析、对象键排序并重新序列化后，语义哈希完全一致。

因此本次“当前 Codex 版本暂不兼容”是误报，升级只是触发条件，不是实际协议破坏。

Codex 官方文档也明确 app-server 主要用于开发和调试、协议可能变化，并提供按版本生成 Schema 的能力。因此 MeetSieve 必须做能力和语义兼容，而不能假设外部文件字节永久不变。参见 [Codex app-server 官方文档](https://learn.chatgpt.com/docs/app-server)。

### 4.2 新兼容策略

移除“原始 Schema 字节哈希是否完全匹配”这一阻断条件，改成三层检查：

#### 第一层：基础可执行性

- 解析用户配置的 Codex 路径。
- 获取版本、启动 `codex app-server`。
- 区分路径不存在、无执行权限、启动失败和登录缺失。
- 版本号只作为诊断信息和缓存键，不作为兼容性白名单。

#### 第二层：最小语义契约

只校验 MeetSieve 实际读写的 method 和字段：

- 对象属性顺序、空白、换行不参与比较。
- 允许新增可选字段、新增通知、新增无关 Schema 文件。
- 响应解析忽略未知字段。
- 下列变化判定为破坏性变化：
  - MeetSieve 使用的方法被删除；
  - 已使用字段被删除或类型改变；
  - 可选字段变成 MeetSieve 无法提供的必填字段；
  - 已使用枚举值被删除；
  - 请求或响应的联合类型不再接受当前分支。

实现上将当前 `SchemaContract.Files map[string]string` 改为“能力契约”，记录必要 method、JSON Pointer、方向、类型和必填约束。完整文件的规范化哈希仅保留为诊断证据，不再直接决定可用性。

#### 第三层：运行时握手

- 启动后真实执行 `initialize -> initialized -> account/read`。
- 设置页检测完成第二层和基础握手后可显示 Codex 已就绪。
- `thread/start` 不在设置页创建虚假会话；在首次真实业务调用时完成验证。
- 任一响应允许未知字段，必要字段缺失时返回稳定错误分类。
- 第一次业务调用失败时只隔离 Codex，会中录音和实时转写继续运行。

### 4.3 缓存与升级行为

校验缓存键使用：可执行文件真实路径、文件元数据、版本、能力契约版本。Codex 文件变化后自动重新检测，不要求用户手工清缓存。

升级后的预期行为：

| Codex 变化 | MeetSieve 行为 |
| --- | --- |
| JSON 属性顺序或格式变化 | 自动兼容 |
| 新增可选字段或通知 | 自动兼容 |
| 新增与 MeetSieve 无关的方法 | 自动兼容 |
| 必要字段类型变化 | 判定不兼容并显示具体能力点 |
| Codex 未登录 | 显示登录问题，不显示版本不兼容 |
| app-server 无法启动 | 显示启动问题和诊断入口 |

不采用以下方案：

- 每次 Codex 升级后人工更新一组原始哈希；
- 长期锁死或自动降级到 `0.146.0`；
- 仅根据 semver 主次版本决定兼容性；
- 为了绕过检测而完全取消协议检查。

## 5. 实时转写稳定性修改

### 5.1 已确认问题

本次会话已发送约 24.84 秒音频，最近 final 到约 22.08 秒，随后会话被记为 `ASR_PROTOCOL_INCOMPATIBLE`。当前适配器把非二进制消息、服务端帧解码失败、转写事件解析失败等多个原因统一映射为不可重试；协调器因此跳过已有的重连退避，立即进入“实时转写不可用”。

同时，provider 时间只要超过读取瞬间的 `lastSentSample` 就会失败，没有容忍帧边界、毫秒取整或读写并发差异。当前日志只保留通用安全错误码，无法判断实际触发点。

### 5.2 错误分类

| 类别 | 示例 | 是否重试 | 结束条件 |
| --- | --- | --- | --- |
| `connection_interrupted` | 连接关闭、超时、临时网络错误 | 是 | 使用现有 `1s/2s/4s/8s/15s` 退避 |
| `provider_busy` | 限流、服务繁忙 | 是 | 遵循 provider 重试提示，否则使用退避 |
| `auth_rejected` | APP Key 无效、资源未授权 | 否 | 立即提示检查设置 |
| `frame_corrupted` | 单个二进制帧无法解码、非预期消息类型 | 是 | 关闭当前物理连接并从安全边界重连 |
| `event_invalid` | 当前事件字段缺失、时间范围明显异常 | 是 | 不持久化错误事件，重连并保留缺口 |
| `protocol_incompatible` | 新连接在首个有效事件前重复出现相同结构性错误 | 有限确认 | 两次独立连接得到相同结构指纹后才确认 |
| `local_persistence_failed` | final 无法安全入库 | 否 | 停止 ASR，录音继续，避免显示未持久化文本 |
| `local_backpressure` | PCM/final 队列持续超限 | 否 | 停止 ASR，记录缺口，录音继续 |

“一次解析失败”不再等同于“协议不兼容”。只有跨独立连接重复出现、且发生在首个有效事件前的确定性结构错误，才允许提前确认协议不兼容；会中偶发错误必须走完整重连预算。

### 5.3 时间边界容错

将单一 `lastSentSample` 判断改为明确的已写入边界：

1. WebSocket 写入成功后原子更新 `lastWriteAckSample` 和最近帧样本数。
2. provider 时间先按毫秒精确换算样本，再与已确认写入边界比较。
3. 允许范围为一个最近 PCM 帧或 provider 毫秒取整误差，两者取较大值，但上限为 200ms。
4. 在容忍范围内，将事件终点钳制到 `lastWriteAckSample`，并记录脱敏计数；不因边界抖动终止会话。
5. 超过上限时不持久化该事件，按 `event_invalid` 重连；最近 final 之后的范围作为转写缺口。

该容错只处理边界表示误差，不允许把 provider 未实际对应的内容写入未来时间段。

### 5.4 重连和缺口处理

- 录音 PCM 先成功写入本地 WAV，再进入 ASR 队列，保持现有核心顺序。
- 物理连接失败后，逻辑会话进入 `recovering`，已有 final 不回滚。
- 重连从当前安全恢复点继续；不能重放的范围写入明确 gap。
- partial 永不作为 final 补写；未收到 final 的文本仍只能作为缺口证据。
- 成功收到新连接的第一个有效事件后清零连续失败计数。
- 用户主动点击“再次重试”会开启新的恢复预算，不覆盖已有录音或 final。

### 5.5 可观测性

新增脱敏诊断字段：

- `failure_stage`：connect/read/decode/parse/map/persist；
- `reason_category`；
- provider frame 类型、长度、压缩标记，不记录原始帧；
- `last_write_ack_sample`、provider 起止毫秒、容忍量；
- 连接代次、重试次数、最近 final 边界；
- provider request/log ID 只保留不可逆摘要或短尾标识。

应用日志必须保留底层 cause 链；UI 和数据库状态只保存稳定错误码与脱敏摘要。不得记录 APP Key、原始音频、完整转写正文或访客令牌。

## 6. 局域网访客页修改

### 6.1 已确认问题

本次链接中的 `192.168.24.54:59935` 在宿主机上可连接，API 路由也能返回预期鉴权响应，说明不是“同一 Wi-Fi 一定互相不可达”的一般网络问题。真正失败点是当前运行二进制没有嵌入 Guest 构建产物，导致 `/join` 返回 404。

当前 `cmd/meetsieve/main.go` 忽略 `fs.Sub` 错误，`registerWebRoutes` 在资源为空时静默返回；LAN runtime 只要监听成功就标记为 `serving`。因此 UI 显示了一个实际上不存在的入口。

### 6.2 构建和启动前检查

- 正式构建必须先生成 `frontend/dist/guest/guest.html` 和对应哈希资源，再执行 Go embed。
- 构建任务在访客入口或其引用资源缺失时直接失败，不生成不完整安装包。
- 开发流程也必须显式执行 Guest 构建；不得依赖开发者恰好运行过一次生产构建。
- `fs.Sub`、`SetGuestAssets` 和路由装配错误不得忽略。
- Guest 是可选能力，因此资源缺失不阻止桌面应用录音，但 LAN 状态必须为 `failed`，且不得展示可复制链接。

### 6.3 端到端就绪判定

LAN 进入 `serving` 前依次完成：

1. 选定网卡仍存在且地址有效；
2. Guest 资源预检通过，`guest.html` 及引用的 JS/CSS 均可读取；
3. 监听指定局域网地址成功；
4. 使用实际 handler 完成本机 `/join` 请求，必须返回 200 且 Content-Type 正确；
5. API 健康路由返回预期状态；
6. 以上结果写入 runtime snapshot 后才生成并展示入口。

本机自检失败时立即停止该 generation、轮换临时令牌并进入 `failed`，避免泄漏不可用链接。重试必须重新选择当前有效网卡并生成新令牌。

### 6.4 区分应用故障和局域网故障

当宿主自检通过但其他设备仍打不开时，UI 不再只显示“连接同一 Wi-Fi”，而是按顺序提示：

- 两台设备是否处于同一子网；
- 是否连接了访客 Wi-Fi或开启 AP/client isolation；
- 宿主或访客设备是否启用 VPN/代理；
- 系统防火墙是否阻止 MeetSieve 入站连接；
- 当前选择的网卡/IP 是否已变化。

这些检查用于定位网络问题，不替代宿主端 `/join=200` 的应用自检。

## 7. 用户可解决的故障反馈

### 7.1 统一内容结构

所有持续性故障 Notice 使用固定顺序：

1. **事实**：哪项能力出了什么问题；
2. **影响**：哪些功能不可用，哪些仍正常；
3. **系统动作**：是否正在自动恢复、已尝试几次；
4. **用户动作**：主操作和次操作；
5. **诊断信息**：稳定错误码和可复制诊断编号。

禁止使用只有结论、没有解决方式的文案，例如“当前版本暂不兼容”“实时转写暂不可用”“运行中”但入口不可访问。

### 7.2 建议文案

| 场景 | 建议文案 | 操作 |
| --- | --- | --- |
| ASR 自动恢复中 | 实时转写连接中断，正在第 {n}/{limit} 次恢复。录音与本地保存正常。 | `立即重试` |
| ASR 恢复失败 | 实时转写未能恢复。录音仍在本地保存，最近 final 之后的范围已记为转写缺口。诊断编号：{id} | `再次重试`、`检查转写设置`、`导出诊断` |
| Codex 可执行但未登录 | Codex 尚未登录，AI 功能暂不可用。录音和实时转写不受影响。 | `打开登录说明`、`重新检测` |
| Codex 真正协议不兼容 | Codex 的必要接口发生变化，AI 功能暂不可用。当前版本：{version}；诊断编号：{id} | `重新检测`、`查看解决方法`、`导出诊断` |
| LAN 资源缺失 | 访客页资源不完整，当前不能生成可用入口。录音和实时转写不受影响。 | `重新检测`、`更新或重新安装 MeetSieve`、`导出诊断` |
| LAN 宿主自检通过但设备不可达 | 访客页已在本机运行，但尚未收到其他设备连接。请检查同一子网、访客 Wi-Fi 隔离、VPN 和防火墙。 | `重新选择网络`、`显示入口`、`查看排查步骤` |

上述属于用户可感知文案和交互变更。实施前按设计系统规则确认文案，并同步更新 `CONTENT.md`、`PRODUCT-PATTERNS.md`、组件 Preview 和视觉基准。

## 8. 接口与数据调整

### 8.1 Wails DTO

在现有 ASR、Codex、LAN 独立状态中补充统一诊断字段，不合并成一个模糊的“系统状态”。旧字段保留一个版本，前端优先读取新字段，避免一次变更破坏已有绑定。

### 8.2 持久化

- 继续持久化稳定错误码、最近 final、gap 和 LAN generation 状态。
- 新增 `reason_category`、`diagnostic_id` 和最后恢复次数时，优先复用现有 metadata/diagnostic 机制；只有确需跨重启展示时才增加 SQLite migration。
- provider 原始 payload、音频内容、完整 token 和完整外部请求 ID 不进入数据库。
- 会议结束后的恢复任务不得修改原始录音，只能追加派生产物或诊断记录。

### 8.3 错误码

保留现有对外错误码兼容性，同时增加更准确的分类，例如：

- `ASR_RECOVERING`
- `ASR_EVENT_INVALID`
- `ASR_PROTOCOL_INCOMPATIBLE`
- `CODEX_NOT_LOGGED_IN`
- `CODEX_START_FAILED`
- `CODEX_PROTOCOL_INCOMPATIBLE`
- `LAN_GUEST_ASSETS_MISSING`
- `LAN_GUEST_SELF_CHECK_FAILED`
- `LAN_NETWORK_UNREACHABLE`

## 11. 测试方案

### 11.1 Codex 契约测试

- Schema 仅属性顺序、空白变化：通过。
- 新增可选字段、通知、无关文件：通过。
- 必要字段删除、类型改变、必填条件收紧：失败并指出 JSON Pointer。
- 未登录、路径错误、app-server 启动失败：分别返回准确错误分类。
- 使用实际安装的当前 Codex CLI 执行生成 Schema 和基础握手。
- CI 保留一个冻结基线版本，并增加当前支持版本矩阵；不能只测仓库 fixture。

### 11.2 ASR 测试

- 单个损坏帧或非预期消息：进入恢复，不立即 `unavailable`。
- 同一确定性结构错误跨独立连接重复：最终判定协议不兼容。
- provider 时间在容忍范围内：钳制并继续。
- provider 时间明显超前：该事件不入库，重连并记录 gap。
- 连接在多个 final 后中断：已有 final 保留，新连接可继续。
- 重连预算耗尽、用户手动重试、会议结束时 tail 处理均可重复验证。
- 真实 provider 长时 E2E 覆盖当前 async two-pass endpoint；禁止用假数据声明真实链路完成。

### 11.3 LAN 测试

- Guest 产物缺失：构建失败；运行时不得显示 `serving` 或链接。
- `guest.html` 存在但引用资源缺失：预检失败。
- 编译后的正式二进制启动后 `/join` 返回 200，静态资源返回正确类型。
- API 未携带 token 返回预期 401，用于证明路由存在而非误判服务异常。
- 端口占用、网卡消失、IP 变化：进入准确失败状态并可重试。
- 使用另一台真实局域网设备完成扫码/打开、鉴权、会议信息读取。
- 覆盖 AP isolation、VPN 和系统防火墙场景的诊断提示。

### 11.4 核心不变量测试

对每个 ASR、Codex、LAN 故障注入都必须验证：

- 本地录音没有停止或截断；
- 已持久化 final 没有回滚或重复；
- 不会显示虚假的“运行中/可用”；
- 错误状态包含影响范围、动作和诊断编号；
- 日志、DTO、SQLite 和诊断包不泄漏凭据、完整 token、原始音频。

## 12. 验收标准

1. Codex `0.146.1` 在语义未变化时自动通过检测，不要求降级或手工更新哈希。
2. Codex 新增可选字段不阻断；真实必要契约变化仍能准确阻断。
3. 单次 ASR 帧解析或边界抖动不再立即导致整场实时转写不可用。
4. ASR 自动恢复期间录音和本地保存持续正常，已有 final 不丢失。
5. ASR 最终失败时准确保留 gap，并给出可操作的恢复入口。
6. LAN 只有在 Guest 页面和 API 最小闭环通过后才显示“运行中”。
7. 任何正式构建都不能产出缺失 Guest 资源但仍显示 LAN 可用的安装包。
8. 用户不打开日志即可区分登录、版本协议、资源缺失、服务启动和局域网隔离问题。
9. 三项外部能力任一失败都不会中断本地录音，也不会把部分成功表述为完整成功。

## 13. 风险与回滚

| 风险 | 控制措施 | 回滚方式 |
| --- | --- | --- |
| 兼容检查过宽，放过真实 Codex 破坏 | 只忽略未知可选内容；必要 method/字段和真实握手仍为硬门槛 | 回滚能力契约版本，不恢复原始字节哈希 |
| ASR 容错写入错误时间 | 容忍上限 200ms、只钳制到已确认写入边界、超限事件不入库 | 关闭边界钳制，保留重连和诊断分类 |
| ASR 重试延迟暴露永久不兼容 | 首事件前相同结构指纹允许两次连接后提前确认 | 调整恢复策略参数，不影响录音链路 |
| LAN 自检增加启动耗时 | 使用进程内 handler 检查和短超时本机请求 | 只保留资源预检与 handler 测试，但不得退回“监听即 serving” |
| 新状态字段影响旧前端 | DTO 字段增量发布并保留旧字段一个版本 | 前端回退旧展示，后端准确状态继续保留 |

## 14. 需要同步修订的既有决策

- Step 7 中“必要 Schema 哈希匹配”修订为“必要能力语义契约匹配 + 运行时握手”；原始字节哈希不再是可用性门槛。
- Step 4 中 `ASR_PROTOCOL_INCOMPATIBLE` 的触发条件收窄；单次解析错误进入可恢复分类。
- LAN 的 `serving` 语义修订为 Guest 页面和 API 已通过最小闭环，不再只代表 listener 已启动。
- 设计系统中补充 `recovering`、诊断编号和解决动作的统一表达。

本方案不通过削弱令牌校验、路径隔离、持久化完整性或隐私保护来换取表面稳定性。修改目标是删除脆弱且没有真实收益的限制，同时让真正必要的限制具备证据、诊断和恢复路径。
